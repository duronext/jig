## Synthesis

### Convergent risks

#### ⚠️ Silent file-lookup failures from duplicated, under-specified branch sanitization
- **Flagged by:** handoff-premortem, api-premortem, integration-premortem, observability-premortem
- **Horizon:** both
- **Narrative:** The string `branch with '/' replaced by '-'` is duplicated inline in four places — `core/skills/premortem/SKILL.md:360`, `core/skills/pr-create/SKILL.md:219` and `:228`, `core/skills/pr-respond/SKILL.md:~140`, `core/skills/postmortem/SKILL.md:78`. Branches containing `.`, `:`, spaces, or multi-segment paths produce filename collisions or near-collisions (e.g., `release/2026.05/cutover` vs `release/2026.05-cutover` both glob-match `*-release-2026.05-cutover-premortem.md`). When the lookup misses, every downstream skill fails *silently*: `pr-create` Step 6 emits no `## Premortem decisions` section, `pr-respond` skips the accept-rationale path, `postmortem` emits no `## Predicted vs Actual` section. There is no log line and no warning — the absence is indistinguishable from "no premortem was run."
- **Decision needed:** ☐ Accept  ☐ Mitigate  ☐ Instrument
- **Suggested mitigation:** Extract a single sanitizer into a framework reference doc (e.g., `framework/BRANCH_SANITIZATION.md`) with a tested regex contract (`[^a-zA-Z0-9._-]` → `-`, collapse repeats, lowercase). Reference it from all four call sites. In each consumer (`pr-create`, `pr-respond`, `postmortem`), require an explicit "premortem file lookup result: found {path} | none-for-branch" log line so a missed lookup is visible in the transcript, not silent.

#### ⚠️ Persisted premortem file is an undocumented multi-consumer contract with no schema version
- **Flagged by:** api-premortem, integration-premortem, observability-premortem, reversibility-premortem
- **Horizon:** 6 months
- **Narrative:** The file at `docs/premortems/{YYYY-MM-DD}-{branch}-premortem.md` (written at `core/skills/premortem/SKILL.md:357`) is produced by `premortem` and parsed by three independent consumers — `pr-create` Step 6 (lines 217-225), `pr-respond` Step 2 (lines 135-150), `postmortem` Step 1.5 (lines 75-97). Each parses the synthesis section, checkboxes, and risk titles with no shared parser, no schema version stamp in the header, and no canonical reader. A contributor who adds a fourth `☐ Defer` checkbox state, renames the `## Synthesis` heading, or extends the Specialist Summary columns silently breaks every consumer. `pr-create`'s regex matches only the three known states; `postmortem` classifies all-Defer risks as MISS. Six months in, third-party packs publish their own producers; the format is frozen by accident.
- **Decision needed:** ☐ Accept  ☐ Mitigate  ☐ Instrument
- **Suggested mitigation:** Stamp `<!-- premortem-schema: v1 -->` into the file header in `core/skills/review/SKILL.md` Stage 7 (the persistence step). Document the schema in a new `framework/PREMORTEM_FILE_FORMAT.md` covering header keys, synthesis section structure, checkbox state vocabulary, and the Specialist Summary table contract. Each consumer reads the schema version and refuses unknown majors with a clear message. Treat this format as a public API from day one.

#### ⚠️ `premortem-detectors` config schema lives in user-editable `jig.config.md` but acts like framework data
- **Flagged by:** api-premortem, integration-premortem, reversibility-premortem
- **Horizon:** both
- **Narrative:** The 18 detector class names (`migrations`, `api-routes`, `auth-ui`, `money-ui`, etc. — `jig.config.md:101-110`) and their glob bodies (hardcoded in `core/skills/pr-create/SKILL.md:62-101`) are split across user config and skill prompt. On day one (1 week), a consumer team who upgraded the plugin runs `pr-create`; Step 0a reads `premortem-detectors` and `premortem-critical-paths` keys that don't exist in their copy of `jig.config.md` because the keys were added only to *this* repo's config, not to `scaffold/jig.config.md`. The skill halts mid-flow with no graceful fallback. At 6 months, `jig init` has copied this verbatim into hundreds of consumer configs; adding a new detector class like `auth-middleware` requires every consumer to manually merge — and renaming `money-ui` silently disables detection for teams pinned to the old key.
- **Decision needed:** ☐ Accept  ☐ Mitigate  ☐ Instrument
- **Suggested mitigation:** Add the six new keys (`premortem-horizons`, `premortem-swarm-tiers`, `premortem-specialist-model`, `premortem-synthesizer-model`, `premortem-critical-paths`, `premortem-detectors`) to `scaffold/jig.config.md` in this PR — non-negotiable. Have `pr-create` Step 0a treat missing keys as "premortem disabled, skip Step 0a entirely" with one log line, not a halt. Move the detector glob definitions out of the skill prompt into a framework file (`framework/PREMORTEM_DETECTORS.md`); let user config override classes by name but inherit globs by default. Mark the config schema "v1, experimental" in a header comment so renames stay cheap for another release.

#### ⚠️ No escape hatch — premortem behavior in `pr-create` cannot be disabled without forking
- **Flagged by:** integration-premortem, reversibility-premortem
- **Horizon:** 1 week
- **Narrative:** `pr-create` Step 0a (lines 53-101) runs unconditionally on every PR creation — it reads the config, walks 18 globs, greps the diff for content patterns. A team with a customized pipeline who wants premortem-aware behavior off has no flag to set; their only option is forking `pr-create`. The same applies to `postmortem` Step 1.5 and `pr-respond` Step 2 premortem-aware blocks. The first consumer to disagree with this default ships a fork that drifts permanently from upstream.
- **Decision needed:** ☐ Accept  ☐ Mitigate  ☐ Instrument
- **Suggested mitigation:** Add `premortem-detection-enabled: true | false` (default `true`) to the Premortem config block in `jig.config.md`. Have `pr-create` Step 0a check the flag first and short-circuit cleanly if disabled. Document the off-switch in `core/skills/pr-create/SKILL.md` so consumers don't have to read source to find it. Same flag gates the parsing blocks in `pr-respond` and `postmortem`.

### Individual risks

#### 🟡 Silent specialist dropout on malformed frontmatter
- **Flagged by:** handoff-premortem
- **Horizon:** 1 week
- **Narrative:** `core/skills/review/SKILL.md` Stage 1 step 5 filters specialists by `stage: premortem` and Stage 2 step 3 intersects globs with changed paths. A specialist with `tier: full` and `stage: premortem` but missing or malformed `globs:` (an easy copy-paste mistake — all six new specialists use identical `globs: ["**/*"]` so the template is fragile) is loaded but contributes nothing to the dispatch. The report comes back with N specialists when N+1 were expected, and no message explains the gap.
- **Decision needed:** ☐ Accept  ☐ Mitigate  ☐ Instrument
- **Suggested mitigation:** In `core/skills/review/SKILL.md` Stage 1, validate each discovered specialist's frontmatter against a minimum schema (`name`, `globs`, `stage`, `model`). On invalid frontmatter, emit a one-line warning to the orchestrator output ("Skipping specialist `foo`: missing `globs`") rather than dropping silently. Reference `framework/SKILL_SCHEMA.md` validation rules.

#### 🟡 "Kickoff hook: planned follow-up" drifts into ambiguity
- **Flagged by:** handoff-premortem
- **Horizon:** 6 months
- **Narrative:** Three files claim a kickoff integration is a planned follow-up: `core/skills/premortem/SKILL.md:300` ("v1: invoke /jig:premortem directly — kickoff auto-prompt is a planned follow-up"), `framework/PIPELINE.md:96-100` ("Note for v1: ... planned as a follow-up"), and `jig.config.md` (the `premortem` concerns entry at line 51 points at the skill directory but implies an integration that isn't wired). A future contributor reading these three sources cannot tell whether the hook exists in a pack, in `team/`, or nowhere. They will rebuild it from scratch, divergent from any in-flight branch, and the `concerns` checklist code-path in `brainstorm` (lines 148-159) will compute `premortem-horizons` differently than the kickoff hook does.
- **Decision needed:** ☐ Accept  ☐ Mitigate  ☐ Instrument
- **Suggested mitigation:** File a tracking issue ("kickoff premortem hook v2") and reference its URL from all three locations as a single source of truth. In `core/skills/premortem/SKILL.md`, change the bullet at line 300 to "**kickoff hook: NOT IMPLEMENTED — see issue #XXX**" so the absence is unambiguous. Remove the `premortem` entry from the `jig.config.md` concerns checklist until the kickoff integration is actually wired.

#### 🟡 `review` is now a four-mode polymorphic monolith with no per-mode integration test
- **Flagged by:** integration-premortem
- **Horizon:** 6 months
- **Narrative:** `core/skills/review/SKILL.md` now branches by `mode` at Stages 1, 2, 3, 5, 6, and 7 (see the new sub-sections at lines 33-37, 105-130, 209-238, 285-301, 322-330, 386-410). A contributor adding a fifth mode (e.g., `mode: spec-review`) who follows the existing pattern at Stages 1, 2, 3, 5, 6, 7 has nothing forcing them to handle every branch. `premortem` mode in particular replaces the logic reviewer with a synthesizer and emits a different scoring section and report header — a refactor that ignores any one of those six branches silently corrupts every premortem run for every consumer.
- **Decision needed:** ☐ Accept  ☐ Mitigate  ☐ Instrument
- **Suggested mitigation:** Add a "Mode integration matrix" table at the top of `core/skills/review/SKILL.md` listing each mode × stage cell with a one-line behavior summary. Anyone adding a mode must fill every cell. Long-term: split mode-specific prose into `core/skills/review/modes/{code,prd,plan,premortem}.md` and have the main SKILL describe orchestration only.

#### 🟡 Synthesizer output schema never validated before persistence
- **Flagged by:** observability-premortem
- **Horizon:** 1 week
- **Narrative:** The synthesizer returns a markdown block which `review` Stage 5 parses (`core/skills/review/SKILL.md:288-301`) and Stage 7 writes verbatim to `docs/premortems/`. There is no validation that the output contains the expected `## Synthesis` heading, the ☐ checkbox glyphs, or a Specialist Summary table. Opus formatting drift — emitting `-` instead of ☐, or omitting the synthesis heading entirely — produces a file the author walks through interactively, then writes accept/mitigate decisions into syntax `pr-create`'s regex cannot parse. The PR ships with an empty `## Premortem decisions` section. Detection comes weeks later via postmortem's `Predicted vs Actual` reporting zero risks against a populated file.
- **Decision needed:** ☐ Accept  ☐ Mitigate  ☐ Instrument
- **Suggested mitigation:** Before persisting in Stage 7, validate the synthesizer output contains: a `## Synthesis` heading, at least one `☐ Accept` / `☐ Mitigate` / `☐ Instrument` triple, and a `## Specialist Summary` table. On validation failure, do not write the file — print the raw output to the terminal and ask the author whether to retry. Add an explicit "output must include literal ☐ glyphs" instruction to `core/skills/premortem/premortem-synthesizer.md`.

#### 🟡 Per-specialist N/A rate is invisible over time
- **Flagged by:** observability-premortem
- **Horizon:** 6 months
- **Narrative:** Each specialist (`api-premortem.md:39`, `backend-premortem.md:50`, etc.) decides for itself whether to return `N/A` based on its own "what to ignore" guard. Stage 4 of `review` collects narratives including N/A entries. Stage 6 records `N/A specialists: count`. But there is no longitudinal view: if `schema-premortem` returns N/A on 87% of diffs that *do* touch schema paths (because its guard over-trims against an aggressive Stage 2 filtered diff), nobody notices — postmortem catches misses per-incident but never aggregates. Months of silent specialist failure.
- **Decision needed:** ☐ Accept  ☐ Mitigate  ☐ Instrument
- **Suggested mitigation:** In the persisted premortem file, record per-specialist N/A status and the changed-path classes the diff actually touched (matched detectors from `pr-create` Step 0a). A periodic `/jig:knowledge-review`-style audit can scan `docs/premortems/*` and flag specialists with anomalous N/A rates against matching path classes.

#### 🟡 `pr-create` Step 0a detector pass is silent when nothing matches
- **Flagged by:** observability-premortem
- **Horizon:** 6 months
- **Narrative:** `pr-create` Step 0a (lines 53-101) prompts the author only when a detector fires. If `premortem-critical-paths` globs break after a consumer renames `checkout/` to `commerce/`, every PR will quietly emit "no detectors fired" and skip the premortem prompt forever. The first signal something is wrong is a payment regression in production.
- **Decision needed:** ☐ Accept  ☐ Mitigate  ☐ Instrument
- **Suggested mitigation:** When zero detectors fire on a diff that crosses a configured `large-diff-loc` threshold, log a one-line note for the PR description: "premortem detectors: 0 fired (diff size: NNN LOC)". Periodic review of these notes surfaces broken critical-path globs. Also: add a `jig doctor`-style command that walks `premortem-critical-paths` against the repo's actual paths to flag globs matching zero files.

#### 🟡 Premortem decisions in PR body have no source-of-truth lifecycle
- **Flagged by:** handoff-premortem
- **Horizon:** 6 months
- **Narrative:** `pr-create` Step 6 (lines 217-225) copies decided risks into the PR body as bullets. If the author later edits the persisted `docs/premortems/*-premortem.md` file (changing an Accept to Mitigate, adding a new risk), the PR body is stale and `pr-respond` may quote outdated rationale to reviewers. Two sources of truth, no reconciliation step.
- **Decision needed:** ☐ Accept  ☐ Mitigate  ☐ Instrument
- **Suggested mitigation:** Make the PR body section deterministic: link to the file with a content hash (`Full premortem: docs/premortems/{filename} @ {git-sha-of-file}`). `pr-respond` re-reads the file and ignores the PR body bullets. Document that the file is the source of truth, the PR body is a snapshot.

## Evolution Notes (post-run, from author)

This consumer-zero run validated the premortem system on its own implementation. Observations:

- **All 8 specialists behaved as designed.** The 3 N/As (frontend, backend, schema) were correct — the diff contains no client-side code, no business logic, no DB migrations. No specialist over-engaged or hallucinated risks. No specialist needs a prompt evolution from this run.

- **Convergence detection worked exactly as designed.** Four risks were independently surfaced by 2+ specialists, and the synthesizer correctly grouped them with `⚠️` icons. The branch-sanitization risk (flagged by 4 specialists from different concern angles — handoff via knowledge decay, api via contract, integration via cross-skill consumption, observability via silent failure) is the clearest example. This is exactly the quality signal the design targeted.

- **The premortem caught real issues the final code review missed.** Specifically:
  - The `scaffold/jig.config.md` gap (premortem-detectors keys won't exist on consumer installs) — concrete, blocking, missed by static review.
  - The no-schema-version-stamp risk on persisted files — convergent 4-way finding, missed by review.
  - The no-off-switch risk for `pr-create` Step 0a — missed by review.
  - The detector schema living in user config vs framework — convergent 3-way, missed by review.

  This is precisely the value proposition: forward review catches what's wrong; premortem catches what becomes wrong because of how it integrates with everything else.

- **One self-referential irony to note for the record:** This very report does not include the `<!-- premortem-schema: v1 -->` header that the synthesizer's own output recommends in the convergent "no schema version" risk. The system identified the gap and could not yet fix itself. That's the perfect first-incident artifact for the antifragile loop the postmortem feedback design promises.
