# Jig 2.0

Jig 2.0 adds the PRD that Jig was missing, and keeps the one it had under a
better name.

## What changed

**Two documents where there was one.** The old `/jig:prd` wrote a technical
contract: API, data, rules, UI states and a layer-tagged acceptance checklist.
That is a spec, so it is now `/jig:spec`, unchanged in substance. The new
`/jig:prd` writes the document a product team means by "PRD":

- one sentence that says what this is for
- who it is for and the moments they see
- rules written as plain behaviours, each with "you'll know it works when"
- phases with an MVP cut line
- milestones, open decisions with owners and dates
- who signs off

It contains no code. When a rule needs steps, it uses plain-language pseudo steps.

**A PRD that stays current.** The PRD publishes as a live Jig page (an
artifact). People tick milestones, record decisions and sign off on it. Jig
writes to the same page from Claude Code:

- `spec` opens decisions it finds in the code
- `build` ticks milestones as their tasks pass review
- the PRD check fills in the trace
- `finish` logs the PR

The contract is `framework/LIVE_PRD.md`.

**A new gate before shipping.** PRD CHECK walks each in-scope outcome from the
user's side. The spec reviewer asks "did we build what the spec says"; the PRD
check asks "can a person now do what the PRD promised".

**Pipeline:**
`DISCOVER → PRD → SPEC → PLAN → BUILD → REVIEW → PRD CHECK → SHIP → LEARN`.

**Review** has four modes: `prd`, `spec`, `plan` and `code`. Four new
specialists review PRDs the way a non-engineer reads them:

- `plain-language`
- `mvp-cut`
- `testable-outcomes`
- `missing-moments`

**The Jig artifact kit.** `core/skills/prd/reference/` holds the page kit:

- `base.css`, `live.js`, `toc.js` and `assemble.sh`
- a starter `template.html` and an exhaustive `showcase.html`
- `components.md` and `voice.md`

Pages carry the Jig look: drafting-paper grid, indigo for the work, a pink
"markup pen" for changes and decisions, dashed phantom lines for things
outside, and a title block for sign-off.

**New mark.** The clamp: two corner brackets holding an indigo square. It
replaces `assets/jig.png` in the README and joins the wordmark on the
microsite, its favicon and its social card.

## Upgrading from 1.x

Run `/jig:init` and choose **Upgrade to 2.0**. It renames config keys
(`prd-swarm-tiers` → `spec-swarm-tiers`, adds `prd-publish` and the new
`prd-swarm-tiers`), renames old technical `*-prd.md` files to `*-spec.md`,
and updates plan headers. See `core/skills/init/reference/upgrade.md`.

Plans written for 1.x keep working: the spec reviewer treats a `> **PRD:**`
header that points at a layer-tagged checklist as a spec.

## Concessions

Choices made to ship 2.0, with what they cost.

1. **Live writes need artifact tools.** Jig updates the page with the
   `ArtifactData` tool, which exists in Claude Code sessions that can publish
   artifacts. Gemini, Codex and CI fall back to file mode: the same events are
   written into the `*-prd.md` (ticked milestones, a `## Log` section).
2. **Sign-off records who pressed, not who was named.** The page's database
   permissions follow sharing levels (Contributor and up can write), not named
   people. Anyone with Contributor access can press "Record sign-off" on any
   approver row. The page stamps the real account that pressed it, so a wrong
   sign-off is visible, but it is not prevented. Jig itself never writes
   sign-offs.
3. **The log is one record per entry with no pruning.** The page shows the
   newest 150. An artifact database holds 25,000 records, far beyond a PRD's
   life, so pruning was left out.
4. **Decisions are authored as two options.** The page renders any number of
   options, but the skill and reviewers steer to A/B with a recommendation.
5. **Page tests run in a browser, not in CI.** `core/skills/prd/reference/test/run.sh`
   loads the assembled template in headless Chrome with a fake
   `window.claude` (an in-memory database) and drives it like a person:
   ticking and reopening milestones, choosing and reopening decisions
   (including one Jig opens later), signing off across revs, adding notes,
   a write landing mid-click, log-only and change failures, the trace,
   HTML in log text, a retried log write, and the contents sidebar. 26 checks, against a fake
   database with network-like latency. It needs Chrome, so it is a local check
   rather than a CI job, and it tests against a fake of the platform's
   database rather than the real one.
6. **The PRD check trusts the agent's observation.** "Verified" means the
   agent (or a person) watched it work and wrote down how. Nothing forces that
   proof to be true; the proof text is shown on the page so readers can judge.
7. **`template.html` was derived from `showcase.html` once.** They share
   `base.css`, `live.js` and `toc.js`, so behaviour cannot drift. Example copy
   and section markup can, and new components should be added to both.
8. **Historical documents keep their old wording.** Jig's own
   `docs/plans/*-prd.md` files were technical PRDs, so they were renamed to
   `*-spec.md` and their plan headers updated (the same upgrade consumers
   run). Their bodies, and `docs/specs/2026-03-28-jig-framework-design.md`,
   still say "PRD" in the 1.x sense; they record what was decided at the time.
9. **Fonts load from Google Fonts.** Pages fall back to system fonts offline.
10. **Two people setting the same field at once: the later one wins.** The
    page merges its fields on the server, so a change to *other* fields
    (Jig's note on a milestone) is never lost, and the tests check that a
    write landing mid-click survives. Two people ticking and unticking the
    same box in the same second still end on whichever click arrived last;
    the log records both.
11. **Some failure modes are untested.** The fake database in the tests does
    not simulate read-only viewers or revoked access.
12. **The stage key for BUILD is still `execute`.** Renaming it would break
    every 1.x config for no gain; the docs name the key where it matters.
13. **The walkthrough's PRD and Spec voiceovers are scripted, not recorded.**
    The 1.x narration was made with ElevenLabs in a voice only the owner's
    account has, and a mismatched synthetic voice would sound worse than
    silence. `docs/audio/SCRIPTS.md` holds both scripts; the walkthrough
    plays `voiceover-prd.mp3` and `voiceover-spec.mp3` as soon as they exist
    and stays silent until then. The stale 1.x PRD narration no longer plays.
14. **The voice rules are enforced by review, not by tooling.** The
    `plain-language` specialist flags banned words and code; nothing blocks
    publishing a page that ignores it.

## Follow-ups

- Run `test/run.sh` in CI once the repo has a workflow with Chrome.
- Per-person sign-off, if artifact databases gain person-level write rules.
- Specs as living documents (merge each shipped spec into a per-area record),
  as OpenSpec does with its change deltas.
